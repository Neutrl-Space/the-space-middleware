Monitoring and alerts

NSBP-192 · Setup draft · November 17, 2026

What this first implementation covers

The authenticated GET /api/health endpoint checks read access to Becoming Access submissions, raffle storage and the connected Shopify shop. It returns HTTP 200 only when all three respond; dependency failures return 503. Empty accessible tables are healthy. This is a dependency check, not an end-to-end form submission test.

Becoming Access and raffle handlers emit one request_capture_failure JSON event for a 5xx, an unhandled exception, or a disconnected response. A saved request with deferred Shopify sync also emits an event despite its HTTP 200 response. Logs contain only a fixed route name, reason, status and elapsed milliseconds. They exclude submitted fields, emails, headers, secrets and upstream error messages.

1. Deploy the health check

  1. Generate a separate random monitoring secret of at least 32 characters using your password manager.
  2. Add MONITORING_SECRET to the intended Vercel environment. Do not reuse the Shopify, Supabase, admin or cron secret.
  3. Deploy this branch to a preview first. Verify authorized health returns 200, and no/mismatched authorization returns 401. Missing configuration returns 503.
  4. After review, merge and deploy to production. Never put the monitoring secret into a query string, theme setting, browser script, screenshot or Jira comment.

2. Configure external uptime monitoring

Recommended starting cadence: every five minutes, with a confirmation retry before opening an incident. Check supported intervals and notification options in the selected plan before enabling them. Configure incident/recovery emails to the agreed recipients; the scope proposes Mudi and Michelle. Phone/SMS options and pricing require a separate choice.

3. Prove notifications work

First validate a failing dependency using the automated tests. Then exercise the monitoring service's test notification and recovery workflow with agreed recipients. Do not deliberately break the storefront, revoke production credentials or flood the real form to test alerting.

Work still needed before completing NSBP-192

  • Create and activate the external monitors and verify delivery to agreed recipients. Nothing in this branch creates an account or sends notifications.
  • Choose a supported log-alerting/forwarding path for individual request failure events. Five-minute health checks cannot detect every transient failed POST.
  • Add a daily synthetic submission in a dedicated test environment or isolated test campaign, including persistence verification and explicit exclusion from demand counts and customer marketing. Validate safe cleanup before enabling.
  • Add daily read-only pre-order inventory checks: internal ship date present; every variant has tracked inventory; continue-selling off. The November 16 decision hides public ship dates, but current purchase logic still requires an internal date. Verify current business rules before changing it.
  • Include queue/deferred-sync age checks and a scheduler heartbeat. A database responding does not prove its worker is running or its email was delivered.
  • Record alert ownership and an incident response procedure. Review monitoring costs and account ownership before enabling paid features.

Responding to incidents

  1. Identify whether a storefront page, storage probe or Shopify probe failed.
  2. Check Vercel deployment/runtime logs and provider status pages. Use request_capture_failure to locate capture failures.
  3. Check Supabase submissions before asking someone to resubmit. A deferred Shopify sync means the original request may already be saved.
  4. Retry only the affected saved job using the relevant existing runbook; do not recreate requests or grant marketing consent.
  5. Verify recovery, then record cause, affected time range and corrective work in Jira.
