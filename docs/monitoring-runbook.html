Monitoring and alerts

NSBP-192 · Production review · November 25, 2026

What this first implementation covers

Current next tasks and ownership. The preorder extension below is prepared for review; it is not active until deployed and configured.

The authenticated GET /api/health endpoint checks read access to Becoming Access submissions, raffle storage and the connected Shopify shop. It returns HTTP 200 only when all three respond; dependency failures return 503. Empty accessible tables are healthy. This is a dependency check, not an end-to-end form submission test.

Becoming Access and raffle handlers emit one request_capture_failure JSON event for a 5xx, an unhandled exception, or a disconnected response. A saved request with deferred Shopify sync also emits an event despite its HTTP 200 response. Logs contain only a fixed route name, reason, status and elapsed milliseconds. They exclude submitted fields, emails, headers, secrets and upstream error messages.

1. Deploy the health check

Sentry error reporting first

Create a Node.js project named the-space-middleware. This implementation uses only error events via a dedicated manual client, with automatic integrations, tracing, profiling and SDK logs disabled. It reports the approved route, reason, status and elapsed milliseconds; raw exceptions and customer/request data are not transmitted. It captures handled 5xx responses and deferred Shopify sync as well as exceptions thrown from the wrapped Becoming Access and raffle handlers. It does not claim to capture every crash before a handler starts.

  1. In Vercel → this project's Settings → Environment Variables, add SENTRY_DSN using Copy DSN on the Sentry setup page. Start with Preview only.
  2. Set SENTRY_ENABLED=true for Preview. Environment is taken from VERCEL_ENV, unless SENTRY_ENVIRONMENT overrides it.
  3. Deploy the monitoring branch as a preview. For a controlled local test, put those two variables and SENTRY_ENVIRONMENT=preview in this checkout's ignored .env, then run npm run monitoring:test-sentry. This emits only a synthetic event; it does not submit a form, change inventory or create a customer.
  4. Find the event in Sentry Issues under the preview environment. Test notification delivery to the agreed recipients separately; seeing an issue is not proof an email arrived.
  5. Configure production issue alerts for request-capture errors and confirm email delivery before enabling in Production. After adding production variables, redeploy. Phone or paid notification features require a separate choice.

The DSN belongs in server environment variables, not a committed source file. An API/auth token is not needed for this event-only integration. Error events are flushed with a bounded wait before failed JSON responses so serverless execution can finish sending them. Transport failures cannot change the form's original response.

Verify the deployed preview

After confirming the local event and test notifications, send an authenticated POST /api/health?test=sentry to the current preview URL with the same monitoring Authorization header. This action is disabled unless Vercel reports VERCEL_ENV=preview. It also requires Sentry to be enabled and its environment to be preview (or unset, inheriting Vercel's preview environment).

The expected response is intentionally HTTP 503 with {"status":"synthetic_failure","test":true}. It uses the same failure wrapper as the real forms but does not read/write customer records or contact Shopify. Confirm the new issue Request capture: monitoring-test / server_error and both configured notification deliveries. Repeating it groups into the same issue, so a new-issue-only alert will not fire again merely because another event arrives.

  1. Generate a separate random monitoring secret of at least 32 characters using your password manager.
  2. Add MONITORING_SECRET to the intended Vercel environment. Do not reuse the Shopify, Supabase, admin or cron secret.
  3. Deploy this branch to a preview first. Verify authorized health returns 200, and no/mismatched authorization returns 401. Missing configuration returns 503.
  4. After review, merge and deploy to production. Never put the monitoring secret into a query string, theme setting, browser script, screenshot or Jira comment.

Daily check heartbeat

Create a Better Stack heartbeat named NEUTRL SPACE Daily Submission Check: every 1 day, with a 2 hour grace period, primary responder email, and no automatic escalation to the entire team. Store its private URL as environment secret BETTERSTACK_HEARTBEAT_URL in GitHub's monitoring-test environment. Use the generated HTTPS URL on incidents.betterstack.com/api/v1/heartbeat/...; never commit it or paste it into tickets.

The workflow sends a bounded GET only after checkout, installation and the submission probe succeed on main. Branch tests and intentional alert failures cannot reset the timer. Missing/invalid configuration or a delivery failure fails the heartbeat step with redacted diagnostics. That separate step uses GitHub failure notifications; it does not emit a Sentry event. Failed probes retain their existing Sentry alerts and do not send a heartbeat.

After merging this change, manually run the normal workflow on main and confirm the heartbeat leaves Pending and shows a recent receipt. Monitoring begins with the first request. Better Stack alerts after 24 hours plus the 2 hour grace period without a successful receipt. Confirm recipient delivery separately; a green workflow alone does not verify email delivery. Manual successful main runs also reset the timer. This heartbeat covers the daily submission probe, not the newsletter worker.

Daily preorder configuration check

Authenticated GET /api/health?check=preorders reuses the middleware's existing server-side Shopify connection. It reads all catalog pages and every variant page for flagged non-archived products, including drafts. It does not read customers or orders, load inventory quantities, run mutations, alter flags/dates/stock, or change any purchase behavior. It requires existing Shopify product read access (InventoryItem.tracked is available with read_products or read_inventory). The ordinary health URL is unchanged.

  • custom.preorder must be a boolean. A true flag requires a valid calendar date in custom.preorder_ship_date.
  • Every preorder variant must have inventoryItem.tracked=true and inventoryPolicy=DENY.
  • Zero stock is allowed. No new future-date rule, public ship-date copy, stock allotment, or automatic repair is introduced.
  • The scan has a 20 second deadline and a 200-query limit. Incomplete responses, repeated pagination cursors, missing variants, denied access and timeouts fail the check; partial scans cannot return green. No preorder products is a valid result and is visible in the counts.
  • HTTP 503 reports either invalid with findings or check_failed without upstream details. Reports include product/variant IDs, product handles and fixed reason codes. At most 100 findings are returned, with a full count and truncation flag. GitHub logs only counts, IDs and fixed reason codes.
  1. Review, push and merge the follow-up monitoring change. Verify the production Vercel deployment contains it before testing. The existing health function has a 60 second platform allowance; no new function is added.
  2. Create GitHub environment monitoring-production. Add secret MONITORING_SECRET with the same value already used by the production Better Stack backend monitor. Do not copy production Shopify or Supabase keys into GitHub.
  3. Create a Sentry alert for the middleware project, environment production, tag monitoring=preorder, route daily-preorder. Include new issues, regressions and recurring failures with the agreed throttle. Reasons are configuration_invalid or check_failed. The existing request_capture-only rule does not match these events. Use the agreed email/Slack recipients and verify delivery. Sentry events contain fixed metadata only, without catalog values, customer fields or secrets. Auth failures before a scan and network failures are reported by GitHub's failed job rather than this Sentry rule.
  4. Run Actions → Daily preorder configuration check → Run workflow → main. The workflow can run only on main. Inspect product/variant IDs for findings; open the corresponding product in Shopify admin and agree any fixes separately. An unavailable deployment, failed authentication or incomplete response also fails the job.
  5. After a complete verified run and alert routing, set repository variable MONITORING_PREORDER_ENABLED=true. The daily schedule is 06:37 UTC / 07:37 Africa/Lagos. The job has a 3 minute overall limit and a 45 second HTTP timeout, and uses only built-in Node fetch.
  6. Keep GitHub Actions failure notifications enabled. This workflow is independent of the isolated submission probe and its existing heartbeat. That heartbeat does not establish preorder coverage; a separate preorder heartbeat is needed if missed-run alerting is required. Neither workflow replaces fulfillment or newsletter worker monitoring.

Responding to incidents

  1. Identify whether a storefront page, storage probe or Shopify probe failed.
  2. Check Vercel deployment/runtime logs and provider status pages. Use request_capture_failure to locate capture failures.
  3. Check Supabase submissions before asking someone to resubmit. A deferred Shopify sync means the original request may already be saved.
  4. Retry only the affected saved job using the relevant existing runbook; do not recreate requests or grant marketing consent.
  5. Verify recovery, then record cause, affected time range and corrective work in Jira.
