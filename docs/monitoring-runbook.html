Monitoring and alerts

NSBP-192 · Setup draft · November 17, 2026

What this first implementation covers

The authenticated GET /api/health endpoint checks read access to Becoming Access submissions, raffle storage and the connected Shopify shop. It returns HTTP 200 only when all three respond; dependency failures return 503. Empty accessible tables are healthy. This is a dependency check, not an end-to-end form submission test.

Becoming Access and raffle handlers emit one request_capture_failure JSON event for a 5xx, an unhandled exception, or a disconnected response. A saved request with deferred Shopify sync also emits an event despite its HTTP 200 response. Logs contain only a fixed route name, reason, status and elapsed milliseconds. They exclude submitted fields, emails, headers, secrets and upstream error messages.

1. Deploy the health check

Sentry error reporting first

Create a Node.js project named the-space-middleware. This implementation uses only error events via a dedicated manual client, with automatic integrations, tracing, profiling and SDK logs disabled. It reports the approved route, reason, status and elapsed milliseconds; raw exceptions and customer/request data are not transmitted. It captures handled 5xx responses and deferred Shopify sync as well as exceptions thrown from the wrapped Becoming Access and raffle handlers. It does not claim to capture every crash before a handler starts.

  1. In Vercel → this project's Settings → Environment Variables, add SENTRY_DSN using Copy DSN on the Sentry setup page. Start with Preview only.
  2. Set SENTRY_ENABLED=true for Preview. Environment is taken from VERCEL_ENV, unless SENTRY_ENVIRONMENT overrides it.
  3. Deploy the monitoring branch as a preview. For a controlled local test, put those two variables and SENTRY_ENVIRONMENT=preview in this checkout's ignored .env, then run npm run monitoring:test-sentry. This emits only a synthetic event; it does not submit a form, change inventory or create a customer.
  4. Find the event in Sentry Issues under the preview environment. Test notification delivery to the agreed recipients separately; seeing an issue is not proof an email arrived.
  5. Configure production issue alerts for request-capture errors and confirm email delivery before enabling in Production. After adding production variables, redeploy. Phone or paid notification features require a separate choice.

The DSN belongs in server environment variables, not a committed source file. An API/auth token is not needed for this event-only integration. Error events are flushed with a bounded wait before failed JSON responses so serverless execution can finish sending them. Transport failures cannot change the form's original response.

Verify the deployed preview

After confirming the local event and test notifications, send an authenticated POST /api/health?test=sentry to the current preview URL with the same monitoring Authorization header. This action is disabled unless Vercel reports VERCEL_ENV=preview. It also requires Sentry to be enabled and its environment to be preview (or unset, inheriting Vercel's preview environment).

The expected response is intentionally HTTP 503 with {"status":"synthetic_failure","test":true}. It uses the same failure wrapper as the real forms but does not read/write customer records or contact Shopify. Confirm the new issue Request capture: monitoring-test / server_error and both configured notification deliveries. Repeating it groups into the same issue, so a new-issue-only alert will not fire again merely because another event arrives.

  1. Generate a separate random monitoring secret of at least 32 characters using your password manager.
  2. Add MONITORING_SECRET to the intended Vercel environment. Do not reuse the Shopify, Supabase, admin or cron secret.
  3. Deploy this branch to a preview first. Verify authorized health returns 200, and no/mismatched authorization returns 401. Missing configuration returns 503.
  4. After review, merge and deploy to production. Never put the monitoring secret into a query string, theme setting, browser script, screenshot or Jira comment.

3. Prove notifications work

First validate a failing dependency using the automated tests. Then exercise the monitoring service's test notification and recovery workflow with agreed recipients. Do not deliberately break the storefront, revoke production credentials or flood the real form to test alerting.

Daily request capture check using the existing Supabase project (prepared, disabled)

npm run monitoring:check-requests invokes the real Becoming Access and raffle handler factories and independently reads saved records. All its table calls, synchronization updates and RPC calls explicitly use monitoring_test; there is no fallback to public. Production reporting continues to use public tables.

First: set up the test schema

  1. Open the existing middleware Supabase project (The Space) → SQL Editor → New query. Paste and run supabase/monitoring-test-environment.sql. This self-contained script creates the test schema, empty tables, schema marker, restricted permissions and test-only RPCs. No production table migrations or data copying are required.
  2. Open the project's Data API settings and append monitoring_test to Exposed schemas. Retain the existing schema entries. Browser roles (anon/authenticated) do not receive access to the test schema.
  3. The schema is ready when the SQL below returns monitoring_test and version 1. Do not enable the schedule yet.
select schema_name, version
from monitoring_test.monitoring_test_environment;

Then: connect the runner and Shopify development store

  1. Create a Shopify development store, install a test app with customer read/write and product read access, and copy its Client ID and Client secret from the app Settings. Keep the app and development store in the same Shopify organization. The runner exchanges these for a fresh access token on each run, so you do not need to maintain a token that expires after 24 hours. Add a test product and variant to a test Becoming Access collection. Before any write, the probe checks Shopify's plan.partnerDevelopment and the shop hostname. A production shop is rejected.
  2. In GitHub repository Settings → Environments, create monitoring-test. Add secrets PROBE_SUPABASE_SERVICE_KEY (server key for the existing middleware project) and PROBE_SHOPIFY_CLIENT_ID / PROBE_SHOPIFY_CLIENT_SECRET (test app credentials). Add environment variables PROBE_SUPABASE_REF (existing project's reference), PROBE_SHOPIFY_SHOP (full myshopify.com hostname), PROBE_COLLECTION_HANDLE, PROBE_PRODUCT_ID and PROBE_VARIANT_ID (numeric IDs). These five configuration values can also be stored as environment secrets; the workflow accepts either, with variables taking precedence if both exist. No additional hosted project or Docker is needed. Keep these secrets out of theme assets and browser code.
  3. A push changing the probe code or workflow on monitoring-and-alerts runs a first check using the monitoring-test GitHub environment, without a production merge. Manual dispatch is also allowed; GitHub requires the workflow to exist on the default branch for dispatch. Scheduled runs alone are gated by repository variable MONITORING_DAILY_ENABLED=true. Leave that variable unset during testing. After review, merge and verify notification delivery before enabling it. Daily schedule: 06:17 UTC (07:17 Lagos), from the default branch.
  4. Enable GitHub Actions failure notifications for the owner and verify a failed run reaches them. This workflow fails visibly in Actions; it does not send a Sentry/Slack event. Independent missed-run heartbeat alerts and agreed recipient delivery remain required before the daily monitoring work is complete.

The shared-project arrangement separates application data by schema; it still shares project capacity and uses a server key with project-wide privileges. The runner pins its calls to the test schema, and its SQL RPCs use schema-qualified tables. This is not a separate project-level security boundary. No existing service keys, permissions on public tables, or production application configuration need to change.

Each run creates a synthetic customer in the development store and test rows in monitoring_test, with email/SMS consent false, monitoring-test customer tag and monitoring-synthetic campaign/event. Test tables reject real email addresses, opted-in contacts and non-test campaigns/events. Records remain for diagnosis; no automated deletion is included. Do not connect the development store to live marketing automations.

This checks application handlers against real database storage and a development Shopify store. It does not test deployed Vercel HTTP routing, browser submission or production Shopify credentials. External uptime and production failure alerts remain separate checks. Test RPCs mirror the relevant production RPC logic and should be reviewed when production migrations change.

Work still needed before completing NSBP-192

  • Create and activate the external monitors and verify delivery to agreed recipients. Nothing in this branch creates an account or sends notifications.
  • Choose a supported log-alerting/forwarding path for individual request failure events. Five-minute health checks cannot detect every transient failed POST.
  • Install the test schema and configure the development store for the prepared daily probe, verify a manual run and failure notification delivery, then enable its schedule. Deployed HTTP route testing and a missed-run heartbeat remain outstanding.
  • Add daily read-only pre-order inventory checks: internal ship date present; every variant has tracked inventory; continue-selling off. The November 16 decision hides public ship dates, but current purchase logic still requires an internal date. Verify current business rules before changing it.
  • Include queue/deferred-sync age checks and a scheduler heartbeat. A database responding does not prove its worker is running or its email was delivered.
  • Record alert ownership and an incident response procedure. Review monitoring costs and account ownership before enabling paid features.

Responding to incidents

  1. Identify whether a storefront page, storage probe or Shopify probe failed.
  2. Check Vercel deployment/runtime logs and provider status pages. Use request_capture_failure to locate capture failures.
  3. Check Supabase submissions before asking someone to resubmit. A deferred Shopify sync means the original request may already be saved.
  4. Retry only the affected saved job using the relevant existing runbook; do not recreate requests or grant marketing consent.
  5. Verify recovery, then record cause, affected time range and corrective work in Jira.
