What the application reports

Route tagSignalMeaning
monitoring-healthauthentication_failed / 401The existing monitoring-secret check rejected a request. Includes health and preorder queries; no dependency scan occurs.
shopify-oauthauthentication_failed / 401The OAuth callback failed its existing state, shop, HMAC or code check. No raw callback values or provider exceptions are logged.
newsletter-workerauthentication_failed / 401Neither the bearer credential nor the short-lived scheduler signature authenticated the request. No worker jobs are run.
newsletter-webhookwebhook_rejected / 401The webhook's existing source/topic/signature verification rejected it. No customer event is enqueued.
newsletter-offerrate_limit_reached / 429The existing durable offer-status limiter rejected a request before Shopify calls. This can also be legitimate polling, a shared network or a client bug; it is not proof of scraping.

Ordinary CORS rejections, invalid form fields, unsupported methods and missing server configuration are not classified as authentication attacks. Existing HTTP responses, consent handling, rate limits and webhook signature checks remain authoritative. A reporting outage cannot grant access. The project-list admin guard also now requires a nonempty configured secret and uses a constant-time comparison; two missing values can no longer grant admin access.

Sentry events have monitoring=security, fixed route/reason/status, environment, optional commit release, and a duration placeholder of zero. The fingerprint separates environment, route and reason. Event bodies, query strings, headers, signatures, authorization codes, IPs, user agents, customer data and raw exceptions are excluded. Vercel application logs contain only fixed signal metadata. The reporter limits security events to the first 20 per route per 5-minute window in each warm process. This is not a distributed/global quota limit. Counts in Sentry are retained signals, not an exact attack-volume measurement; cold starts and multiple instances have independent budgets.

Application alert rollout

  1. Review, push and merge the follow-up monitoring change; wait for a successful production deployment. It uses the existing production SENTRY_ENABLED, SENTRY_DSN and SENTRY_ENVIRONMENT configuration. No new API function, database migration, paid dependency or production secret is needed.
  2. In the middleware Sentry project, create an issue alert named Security signals — Production, environment production, filter monitoring=security. Start with a frequency condition of at least 10 events in an issue over 5 minutes (equivalently more than 9), email plus the agreed Slack destination, and a one-hour repeat throttle. Do not use only a new-issue trigger: it will not measure a burst or keep notifying for recurring incidents. The initial threshold is an operational starting point, not an agreed security policy; tune it after observing normal traffic. Existing request-capture and preorder alert filters do not match these events.
  3. Use Sentry's notification test to check destination configuration. For a controlled authentication test, send ten sequential GET requests to the production health endpoint with an intentionally invalid bearer value. Expect ten 401 responses and no dependency reads or customer writes. This intentionally exercises the actual rejection classification and can notify the configured recipients. Verify the event tags and email/Slack receipt. Do not change the real monitoring secret, webhook settings, inventory or marketing configuration to test.
  4. For suspected abuse, inspect Vercel traffic/firewall data before drawing conclusions or blocking clients. A rate-limit signal alone does not identify an actor or establish malicious intent. Persistent auth failures may also mean a misconfigured monitor or scheduler.

Traffic and scraping coverage

The Shopify storefront serves homepage/product pages directly. Those requests and Shopify-hosted customer/admin sign-ins do not pass through this middleware, so these application events do not cover storefront scraping or failed Shopify account logins. No reliable login-failure feed has been established in this implementation. Confirm the available Shopify/provider signals before promising that coverage. A browser analytics script cannot observe every bot or failed server-side authentication.
